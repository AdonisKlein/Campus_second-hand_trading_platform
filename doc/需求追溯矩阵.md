# 校园二手交易平台需求追溯表

## 1 编写目的与口径

本表将当前验收范围内的需求、业务用例、三层模型、代码模块、测试编号和测试结果放在同一张表中，用于需求评审、课程答辩和回归验收。当前基线为 `REQ01`～`REQ18`、`UC01`～`UC18`，与《业务场景（用例）清单》一致。

三层模型采用项目既有编号：`SYS-SEQ` 表示系统顺序模型，描述参与者与系统边界的交互；`COMP` 表示组件顺序模型，描述前端、Controller、领域服务和外部适配器的协作；`OBJ` 表示对象顺序模型，描述服务、实体、Repository 及状态变化。

测试编号采用 `UNIT-TCxx`、`INT-TCxx`、`E2E-TCxx`。其中“由 INT 覆盖”表示该业务主要依赖 Session、数据库或跨模块协作，没有为了满足编号而重复编写低价值单元测试。2026-08-27 本轮 `mvn verify` 为单元测试 29/29、已执行集成测试 44/44 通过；本机 Docker 不可用，6 项 MySQL Testcontainers 测试被跳过。表中“最近通过”表示引用 2026-08-26 已记录的真实 MySQL 门禁或完整 Compose E2E 6/6 通过结果，本轮没有重新执行这些 Docker 测试。

## 3 覆盖结论与待补强项

- 18 项需求均可追溯到用例、三层模型编号、实现模块和至少一种自动化测试。
- 单元测试集中在验证码/注册、搜索规则、治理规则和当前身份等适合隔离验证的领域；依赖 Session、CSRF、数据库锁和跨模块状态的业务由 API/MySQL 集成测试承担主验证责任。
- 当前完整 E2E 共 5 条业务旅程加 1 条 runner smoke，最近记录为 6/6 通过。旅程按业务闭环覆盖多个用例，因此 `E2E-TC01`～`E2E-TC18` 是需求追溯编号，并不表示存在 18 个独立 Playwright 测试方法。
- 仍需补强的测试包括：UC03 独立 API 集成用例，以及 UC04 资料修改、UC07 下架/重新上架、UC09 留言修改/删除、UC15 我的举报结果页、UC17 留言管理的独立 E2E 断言。相关规则或主闭环已有其他层级覆盖，不影响当前核心流程回归，但应在最终验收前逐项补齐。

## 4 维护规则

需求或 interface 变更时，应在同一轮同步更新《业务场景（用例）清单》、本追溯表、Postman 契约和相关测试。测试结果只能引用实际执行记录；未运行、部分覆盖或仅由其他层级覆盖时必须明确标注。
