# 校园二手交易平台模块设计方案

> 状态：当前实现基线
>
> 适用范围：REQ01～REQ18 / UC01～UC08
>
> 架构形态：模块化单体

## 1. 设计目标

平台已经完成从早期演示项目到安全模块化单体的重构。本方案描述当前模块边界和后续演进原则，不再把已经完成的 Session、图片、私聊、交易和举报治理列为未来工作。

核心目标：

- Web 身份只由服务端 Session 决定。
- 业务规则集中在领域服务，不散落在 Controller 和前端。
- 商品、交易、公开问答、私聊和举报各自拥有清晰的权限边界。
- 数据库通过 Flyway 演进，并用真实 MySQL 并发测试验证关键竞争条件。
- adapter 可以替换，但调用方使用的深 interface 保持稳定。

## 2. 角色与业务边界

| 角色 | 能力 |
| --- | --- |
| 游客 | 浏览、搜索、查看公开商品详情和公开问答。 |
| 学生用户 | 注册登录、维护资料、发布商品、沟通、提交购买意向、参与交易和举报。 |
| 管理员 | 管理公开内容和账号，处理举报并形成审计。 |

买家和卖家只是某笔交易中的临时身份。管理员没有查看学生私聊正文的特殊权限。平台当前不处理支付、退款、物流和评价。

## 3. 总体架构

```text
Browser
  -> Nginx Web / same-origin /api
    -> Spring Security + CurrentActorService
      -> Controller adapters
        -> domain interfaces/services
          -> JPA repositories / MySQL 8.4
          -> ProductImages filesystem adapter
          -> JavaMailSender SMTP adapter
          -> Spring Session JDBC
```

前端是静态 HTML/CSS/JavaScript 应用。`frontend/assets/js/api.js` 是 Session hydration、CSRF 和统一请求入口。后端按业务 package 组织为模块化单体；模块之间通过明确 interface 协作。

## 4. 模块划分

| 模块 | 核心 interface 或服务 | 负责用例 | 关键不变量 |
| --- | --- | --- | --- |
| `security` | `CurrentActorService`、`SecurityConfig` | 全部场景共同约束 | 当前身份只来自有效 Session。 |
| `user` | `RegistrationService`、`VerificationService`、`AuthController` | UC01 | 验证码用途隔离；密码和会话可撤销。 |
| `search` | `CampusSearch` | UC02 | 多关键词交集；结果为安全公开投影。 |
| `media` | `ProductImages` | UC03 | 内容验证、重编码、配额和 owner 路径。 |
| `item` | `SellerInventory`、`ProductDetail` | UC02～UC03 | owner 授权；交易状态与审核状态分离。 |
| `message` | 商品公开留言服务 | UC04 | 公开可见；只能维护本人留言。 |
| `chat` | `DirectChat` | UC04 | 仅参与者可见；sequence 单调；屏蔽阻止发送。 |
| `order` | `TradingService`、`TradeDesk` | UC05～UC06 | 非独占意向；唯一预留；状态统一变更。 |
| `report` | `ContentGovernance` | UC07～UC08 | 对象快照、最终状态、匹配措施和追加审计。 |
| `admin` | 管理员用户/商品/留言服务 | UC08 | ADMIN Session；不能绕过交易状态机。 |
| `common` | 响应、异常和邮件抽象 | 全部 | 对外错误稳定，不泄漏内部异常或凭据。 |

## 5. 关键 interface

### 当前身份

`CurrentActorService` 从 Spring Security/Session 读取当前用户，复核账号状态与角色。Controller 不接受客户端身份字段作为授权依据。

```text
request
  -> Session authentication
  -> CurrentActorService
  -> role / owner / participant check
  -> domain operation
```

### 商品图片

`ProductImages.store/load` 隔离图片验证和存储。当前 adapter 使用文件系统与 Docker 持久卷；未来换 MinIO/S3 时，商品模块调用方式不变。

### 商品详情与卖家管理

`SellerInventory` 集中商品 owner、可编辑状态、卖家下架和重新上架规则。`ProductDetail` 一次返回商品、安全卖家摘要、当前意向和允许动作，前端不复制权限规则。

### 私聊

`DirectChat` 管理会话唯一性、参与者授权、sequence 历史、已读游标、限流和屏蔽。轮询只是当前 Web adapter，未来切换 SSE/WebSocket 不改变消息顺序和授权 interface。

### 交易

`TradingService.requestPurchase/perform` 是交易写入唯一入口：

```text
PURCHASE_REQUESTED
  -> ACCEPT -> WAITING_HANDOVER -> COMPLETE -> COMPLETED
  -> DECLINE -> DECLINED
  -> CANCEL  -> CANCELLED
  -> timeout -> EXPIRED
```

提交购买意向不会改变商品 `ON_SALE`。卖家接受后商品才进入 `RESERVED`；买家确认交接后商品才进入 `SOLD`。取消或预留超时释放商品。

`TradeDesk.browse` 返回买卖视角、阶段统计、商品分组、时间线、剩余时间和允许动作，避免页面拼装领域规则。

### 举报治理

`ContentGovernance.submit/listMine/listForAdmin/decide` 管理举报创建、学生查询和管理员处理。身份分别来自学生或 ADMIN Session；举报处理以行锁和追加审计保证同一记录只能最终处理一次。

## 6. 数据一致性

- 用户、商品、订单、留言、私聊和举报由各自模块拥有。
- 商品交易状态和审核状态使用独立字段。
- 订单保存商品标题、价格和双方昵称快照。
- 私聊消息 sequence 只增不改，已读游标只向前。
- 举报保存对象快照，最终处理历史只追加。
- 关键交易、治理和配额操作使用数据库锁或唯一约束处理并发。

所有表由 `backend/src/main/resources/db/migration/` 中的 Flyway 迁移建立。`database/schema.sql` 只创建空数据库，Hibernate 只执行 `validate`。

## 7. 安全设计

- HttpOnly Session Cookie 表示 Web 登录凭据，JavaScript 无法读取。
- 所有写请求携带 CSRF，CORS 使用精确允许来源。
- 登录、验证码、留言、聊天和举报具有频率或次数限制。
- 禁用账号递增认证版本，旧 Session 不能继续使用。
- 前端本地用户对象只用于渲染，不是身份或权限证据。
- 管理入口默认隐藏，但后端授权仍是唯一安全边界。
- 图片、邮件和异常信息不得泄漏 EXIF、验证码、SMTP 密钥或内部路径。

## 8. 部署 adapter

| 能力 | 当前 adapter | 可替换方向 |
| --- | --- | --- |
| Web Session | Spring Session JDBC | Redis Session |
| 商品图片 | 文件系统 + 持久卷 | MinIO/S3 |
| 验证邮件 | JavaMailSender + 阿里云 SMTP | 其他邮件服务 adapter |
| 私聊更新 | 8 秒轮询 | SSE/WebSocket |
| 数据库 | MySQL 8.4 | 保持关系数据库语义 |

替换 adapter 前必须保留现有 interface、安全不变量和测试契约。

## 9. 部署形态

- 本地推荐 Docker Compose：MySQL、Backend、Web，可选 Mailpit。
- Kubernetes Base：MySQL StatefulSet、Backend/Web Deployment、Service 和持久卷。
- CI 使用 Kind 验证镜像可部署性，不把临时集群宣称为长期生产环境。
- Nginx 同源代理 `/api`；生产启用 TLS 时 Session Cookie 必须启用 Secure。

## 10. 测试与质量门禁

- 单元测试验证独立规则。
- MockMvc API 集成测试验证 Session、CSRF、权限和数据库最终状态。
- MySQL 8.4 Testcontainers 验证迁移和并发竞争。
- Node 契约测试防止页面结构与 Session 行为回退。
- Playwright E2E 验证 UC01～UC08 的核心业务旅程；细粒度功能通过 REQ01～REQ18 追溯。
- 候选镜像只有在测试全绿后才能进入 Compose E2E、GHCR 发布和 Kind 部署门禁。

## 11. 演进原则

后续能力必须由真实需求驱动：

1. 收藏、评价、多图和结构化报价先定义领域状态、权限和追溯测试。
2. SSE/WebSocket 复用现有会话授权和 sequence，不重写消息规则。
3. 多实例部署前替换图片存储和必要的 Session adapter。
4. 只有模块出现独立伸缩、部署或团队所有权需求时才拆微服务。
5. interface 变化同步更新 `PROJECT_CONTEXT.md`、Postman、测试、追溯矩阵和工作日志。
