# 校园二手交易平台重构方案（学生易读版）

> 状态：评审草案 v0.2
> 日期：2026-08-23
> 已按本轮决定更新：邮箱注册登录、三类用户、管理员职责合并。

## 1. 先说结论

这个项目现在是一个能演示基本流程的课程项目，已经有注册登录、浏览搜索、发布商品、商品留言、创建订单和简单管理员后台。

接下来不应该直接把代码全部推倒重写，也不应该简单地把每个 Controller 变成一个微服务。正确顺序是：

1. 先修复登录和权限问题，防止冒充别人。
2. 按真实业务重新整理后端代码。
3. 把商品状态和订单状态做正确，避免一件商品卖给两个人。
4. 再加入图片上传、私聊、收藏、评价和举报等功能。
5. 最后根据真实访问量拆成多个可独立运行的微服务。

首期用户只保留三类：

- 游客。
- 学生用户。一个学生既可以买东西，也可以卖东西。
- 管理员。审核、客服、仲裁、运营、财务等后台功能暂时都由管理员负责。

账号方案改为：

- 邮箱验证码注册。
- 邮箱和密码登录。
- 忘记密码时通过邮箱验证码重置。
- 将来可以增加“学校邮箱验证”，不需要推翻当前账号系统。

## 2. “重构为深领域 Module”是什么意思

后面的方案不再频繁使用这个术语，统一称为“业务模块”。

### 2.1 直白解释

它的意思是：

> 把同一件业务的规则集中放在一个地方，对外只提供几个简单操作。

以“学生下单”为例。

当前代码大致是：

1. 前端自己传 buyerId 和 sellerId。
2. Controller 查询买家、卖家和商品。
3. 检查商品有没有卖掉。
4. 保存订单。
5. 再把商品改成 SOLD。

这里的问题是前端可以伪造用户 ID，而且两个人同时下单时可能都成功。

重构后，页面只需要表达：

    当前登录的学生想购买商品 123

“交易业务模块”自己负责：

- 从登录状态确认当前学生是谁。
- 查出真正的卖家，不相信前端提交的卖家 ID。
- 禁止购买自己的商品。
- 检查商品是否还在售。
- 原子地锁定商品，避免重复出售。
- 保存下单时的商品名称和价格。
- 创建订单并记录操作日志。
- 发送“有人下单”的通知。

页面和其他代码不需要知道这些内部细节。

### 2.2 为什么这样做

- 安全规则只写一次，不会 Web 端写一份、移动端再写一份。
- 修复订单问题时，只需要修改交易业务模块。
- 以后把交易业务拆成单独微服务时，页面基本不用跟着重写。
- 测试可以直接验证“能不能下单”，不用关心内部用了几张表。

### 2.3 它不等于微服务

业务模块是整理代码和业务规则的方法。

微服务是把某些业务模块变成独立运行的程序。

应该先把业务模块整理正确，再决定哪些模块需要单独运行。如果一开始就把现有代码拆成十几个程序，会立刻增加网络调用、部署、日志和数据一致性问题，但原来的业务漏洞仍然存在。

## 3. 用户身份设计

### 3.1 游客

游客不需要登录，可以：

- 浏览首页和商品详情。
- 搜索、分类和筛选商品。
- 查看公开的卖家昵称、学校认证标记和历史评价摘要。
- 查看平台公告和交易规则。

游客不能发布、收藏、私聊、下单、评价或举报。

### 3.2 学生用户

学生用户通过邮箱验证码注册。

同一个账号可以：

- 作为卖家发布和出售商品。
- 作为买家收藏、沟通和购买商品。
- 管理自己的资料、订单、消息和评价。

“买家”和“卖家”不是两种账号，也不需要在注册时选择。某个学生发布商品时是卖家，购买别人的商品时是买家。

### 3.3 管理员

首期只有一个管理员角色，负责：

- 用户管理：禁用、恢复和查看基础资料。
- 商品管理：审核、下架、恢复和处理违规商品。
- 消息和举报：处理被举报的内容。
- 订单和纠纷：查看交易过程、处理取消和争议。
- 评价管理：隐藏辱骂或违规评价。
- 运营管理：分类、公告、Banner 和专题活动。
- 财务管理：以后接入线上支付后查看支付和退款结果。
- 系统管理：查看日志、运行状态和基础配置。

管理员不能由普通注册页面选择，只能通过数据库初始化或受保护的后台操作授予。

即使暂时只有一个管理员角色，每次操作也要记录管理员、操作对象、修改前后状态、原因和时间。

## 4. 功能模块设计

### 4.1 游客和学生功能

| 功能 | 游客 | 学生买家 | 学生卖家 |
|---|---:|---:|---:|
| 浏览、搜索和查看商品 | 可以 | 可以 | 可以 |
| 收藏和关注 | 不可以 | 可以 | 可以 |
| 发布、编辑和下架商品 | 不可以 | 同一账号可以 | 可以 |
| 私聊和议价 | 不可以 | 可以 | 可以 |
| 创建订单 | 不可以 | 可以 | 不能购买自己的商品 |
| 确认或取消交易 | 不可以 | 按订单状态操作 | 按订单状态操作 |
| 当面交接或邮寄 | 不可以 | 可以选择 | 可以处理 |
| 评价对方 | 不可以 | 订单完成后 | 订单完成后 |
| 举报商品或用户 | 不可以 | 可以 | 可以 |
| 管理个人资料 | 不可以 | 可以 | 可以 |

### 4.2 管理员功能

管理员后台首期分成几个页面，但仍属于同一个管理员身份：

1. 控制台：首页数据、待处理事项和异常提醒。
2. 用户管理：查询、禁用和恢复。
3. 商品管理：审核、查询、下架和恢复。
4. 订单管理：查看订单时间线和处理异常订单。
5. 举报管理：处理商品、消息、用户和评价举报。
6. 内容管理：分类、公告、Banner 和活动专题。
7. 支付管理：以后接入支付后的查询、退款和对账。
8. 系统日志：管理员操作记录和系统错误。

## 5. 建议的业务模块

| 业务模块 | 它负责什么 | 它必须保证什么 |
|---|---|---|
| 账号模块 | 注册、登录、验证码、密码重置、登录状态 | 不能冒充别人；验证码和密码安全 |
| 学校验证模块 | 学校邮箱、学校名称、认证状态 | 学校验证可以扩展，不与登录写死 |
| 个人资料模块 | 昵称、头像、简介、隐私设置 | 不随便公开邮箱和手机号 |
| 商品模块 | 草稿、发布、编辑、上下架、分类和价格 | 只有卖家能修改自己的商品 |
| 图片模块 | 上传、压缩、缩略图和安全检查 | 不接受超大、伪造或危险文件 |
| 搜索推荐模块 | 搜索、筛选、热门和个性化推荐 | 数据量大时仍能快速查询 |
| 收藏关注模块 | 收藏商品、关注卖家、浏览历史 | 只允许本人管理自己的记录 |
| 聊天模块 | 会话、消息、未读、已读和议价 | 只有聊天双方可以查看 |
| 交易模块 | 商品预留、订单、取消和完成 | 一件商品不能同时卖给两个人 |
| 交付模块 | 当面交接、交接码、邮寄和确认收货 | 没完成交付不能随便完成订单 |
| 支付模块 | 以后接入支付、退款和对账 | 支付结果不能由前端自己填写 |
| 评价模块 | 买卖双方评价和信誉摘要 | 只有完成交易后才能评价 |
| 举报模块 | 举报商品、消息、用户或交易 | 保留证据和处理结果 |
| 管理员模块 | 统一后台和所有管理操作 | 每次管理操作都可追踪 |
| 通知模块 | 站内通知、邮件和移动推送 | 发送失败可重试，不影响主业务 |

这些模块首期不一定都是单独的程序，但代码目录和数据库访问必须分清楚。交易模块不能绕过商品模块直接乱改商品，管理员模块也不能直接修改所有表。

## 6. 邮箱注册和登录方案

### 6.1 当前版本

注册流程：

1. 学生输入邮箱。
2. 系统生成 6 位验证码。
3. 系统通过你的发信域名发送验证码。
4. 学生输入验证码、密码和昵称。
5. 后端确认验证码正确后创建账号。
6. 注册成功后建立安全登录状态。

登录流程：

1. 学生输入邮箱和密码。
2. 后端校验密码和账号状态。
3. 登录成功后创建会话。
4. Web 使用 HttpOnly Cookie 保存会话，JavaScript 不能直接读取。
5. Windows 和移动端使用系统安全存储保存登录凭据。

忘记密码：

1. 输入注册邮箱。
2. 收取一次性验证码。
3. 验证通过后设置新密码。
4. 原有登录会话全部失效。

### 6.2 对现有验证码代码的改进

当前代码会把验证码输出到控制台，并使用普通 Random，失败次数也没有真正封顶。重构时需要：

- 使用 SecureRandom 生成验证码。
- 数据库只保存验证码摘要，不保存明文。
- 验证码 5 分钟过期，最多尝试 5 次。
- 同一邮箱 60 秒内不能重复发送。
- 按邮箱和 IP 做每小时、每天限流。
- 验证成功或重新发送后，旧验证码立即失效。
- 生产日志中禁止记录验证码。
- 找回密码尽量返回相同提示，避免别人探测哪些邮箱已经注册。

密码使用 BCrypt 或 Argon2 保存摘要，绝不保存明文。建议至少 8 位，并允许密码管理器生成的长密码。

### 6.3 你的域名如何使用

你的域名主要用于“从哪个地址发验证码邮件”，例如：

    no-reply@你的域名

需要在域名 DNS 中配置：

- SPF：声明哪些服务器允许代表你的域名发信。
- DKIM：为邮件添加数字签名。
- DMARC：告诉收件服务器如何处理伪造邮件。

开发阶段可以使用 SMTP 服务商。具体服务商放在邮件发送模块中，以后更换服务商不需要修改注册业务。

### 6.4 将来扩展学校验证

登录邮箱和学校认证邮箱应该是两个概念：

- 学生可以用常用邮箱注册平台。
- 在个人中心选择“认证学校”。
- 输入学校邮箱并接收验证码。
- 后端根据可配置的学校域名判断学校。
- 认证成功后显示“学校已认证”，但不公开完整学校邮箱。

学校认证记录包含学校、邮箱、认证时间、可选到期时间，以及待验证、已验证、已过期、已撤销等状态。

安全注意：

- 必须精确比较邮箱域名，不能只用字符串 endsWith，避免 evilbuaa.edu.cn 一类伪造域名。
- 一个学校邮箱原则上只能认证一个平台账号。
- 邮箱认证只能证明用户能接收该学校邮箱，不一定能证明仍是在校状态。
- 将来可增加统一认证、学籍接口或人工审核，但不需要改变平台注册登录方式。

## 7. 商品和交易流程

### 7.1 商品状态

    草稿 -> 待发布或待审核 -> 在售 -> 已预留 -> 已售出
                                |        |
                                v        v
                              已下架   预留取消后回到在售

“学生自己下架”和“管理员强制下架”要分别记录。

### 7.2 下单过程

1. 买家点击购买。
2. 后端从登录状态得到买家身份。
3. 后端从商品得到卖家和当前价格。
4. 系统尝试预留商品。
5. 如果别人已经抢先预留，返回明确提示。
6. 预留成功后创建订单并通知卖家。
7. 订单取消或超时后，商品自动恢复在售。
8. 交付完成后才把商品标记为已售出。

每次下单都带一个请求唯一编号。网络卡顿导致前端重复发送时，后端仍然只创建一个订单。

### 7.3 订单状态

首期可以使用：

    等待卖家确认 -> 等待交付 -> 等待买家确认 -> 已完成

另外有已取消和争议处理中。

前端不能直接把订单改成任意状态。后端要根据当前是谁、订单现在是什么状态来决定能不能操作。

## 8. Web、Windows 和移动端

推荐方案：

- Web：React/Next.js，负责公开浏览、完整交易和管理员后台。
- Windows：Tauri + React，可以复用大量 Web 页面。
- 移动端：React Native，负责 Android 和 iOS。

三端共享后端接口说明、请求响应类型、登录和错误规则、视觉规范和统计规则，不必强行共享全部页面代码。

推荐开发顺序：

1. 先完成响应式 Web。
2. Web 稳定后制作 Windows 外壳。
3. 同时开发移动端的登录、首页、发布、聊天和订单主流程。
4. 后端对三端提供同一套业务能力，不复制业务规则。

## 9. 微服务怎么拆

### 9.1 第一阶段：先把业务写正确

第一阶段可以保留一个主要 Spring Boot 项目，但内部按业务模块分目录和数据访问范围。

可以先独立的只有图片处理、邮件通知和搜索数据更新任务。这样开发调试简单，也能把高耗时任务移出主请求。

### 9.2 第二阶段：形成第一组微服务

业务稳定后，建议拆为：

1. 网关：统一入口、限流和转发。
2. 账号服务：注册、登录、验证码、会话和学校认证。
3. 商品服务：商品、图片信息、分类和收藏。
4. 交易服务：预留、订单、交付、评价和以后接入的支付。
5. 聊天服务：会话、消息和长连接。
6. 管理服务：用户、商品、举报、订单和运营后台。
7. 搜索服务：搜索和推荐结果。
8. 通知任务：邮件、站内通知和移动推送。

拆分规则：

- 一个服务只能直接修改自己拥有的数据。
- 服务之间通过明确操作或消息通信。
- 订单保存商品名称和价格快照。
- 重要消息允许重复发送，但接收方必须识别重复消息。
- Redis 不保存订单和支付的最终结果。
- 搜索数据可以重新生成，数据库商品才是真实数据。

## 10. 现在最需要修复的安全问题

1. 不再相信前端提交的 userId、buyerId、sellerId、senderId 和 adminId。
2. 使用真正的服务端会话，不把 localStorage 用户对象当身份证明。
3. 只允许自己的 Web 域名跨域调用。
4. 商品标题和描述显示时转义，防止有人发布脚本。
5. 数据库密码改为环境变量，并轮换已经写入过仓库的密码。
6. 生产环境禁止 Hibernate 自动改表，改用版本化数据库脚本。
7. 错误响应不返回程序内部异常。
8. 所有列表增加分页。
9. 图片上传限制格式、大小和数量，并做安全检查。
10. 管理员的所有操作保留日志。

## 11. 分阶段开发计划

每个 Sprint 建议两周。

### Sprint 0：让项目可以稳定开发

- 安装并统一 JDK。
- 增加 Maven Wrapper。
- 建立持续集成测试。
- 把数据库密码移出配置文件。
- 建立数据库版本管理。
- 修复文档和配置不一致。

完成标准：新电脑按文档可以启动项目，自动测试可以运行。

### Sprint 1–2：邮箱账号和安全登录

- 重写验证码发送和校验。
- 以邮箱作为登录账号。
- 正式会话、退出、忘记密码和会话失效。
- 后端统一取得当前登录用户。
- 删除所有由前端决定身份的参数。
- 完成管理员安全登录。

完成标准：修改前端保存的用户 ID 不能冒充别人。

### Sprint 3–4：商品、图片和搜索

- 商品草稿、发布、编辑和下架。
- 多图上传、压缩和安全检查。
- 分类、搜索、筛选和分页。
- 收藏、关注和个人发布列表。
- 预留学校邮箱认证的数据和接口位置。

完成标准：商品功能完整，恶意图片和脚本不能进入页面。

### Sprint 5–6：私聊和交易

- 商品私聊、未读和已读。
- 议价。
- 商品预留。
- 正确订单状态。
- 取消和超时释放。
- 当面交接和确认完成。

完成标准：100 个请求同时购买同一商品，只能有一个成功预留。

### Sprint 7–8：评价、举报和管理员

- 双向评价。
- 举报商品、消息、用户和订单。
- 管理员统一后台。
- 管理操作日志。
- 公告、Banner 和分类管理。

完成标准：管理员能够处理首期所有后台工作，操作都有记录。

后续再增加学校邮箱验证、移动推送、在线支付、退款、邮寄、推荐系统，并根据真实访问量拆微服务。

## 12. 现有代码如何迁移

| 当前代码 | 重构方向 |
|---|---|
| UserController | 账号业务模块；保留邮箱注册但重写安全逻辑 |
| VerificationService | 使用安全验证码、摘要保存、限流和真实邮件服务 |
| EmailService | 改为可替换的 SMTP/邮件服务商发送模块 |
| ItemController | 商品业务模块，不再直接操作数据库 |
| MessageController | 拆分公开问答和私密聊天 |

## 13. 已经确定的决定

- 采用邮箱验证码注册。
- 采用邮箱和密码登录。
- 将来可以增加学校邮箱认证。
- 首期角色只有游客、学生和管理员。
- 学生账号同时具备买家和卖家能力。
- 后台职责首期全部合并到管理员。
- 需要 Web、Windows 和移动端。
- 目标仍是微服务，但先整理好业务模块，再逐步拆分。
