# 从顺序图生成测试用例

## 1. 文档定位

本文只说明如何把当前 8 个业务场景的系统顺序图和对象级顺序图转换为测试，不重复列出《测试清单》中的全部测试步骤和执行结果。

- `SYS-SEQ01～SYS-SEQ08`：描述参与者与系统边界的交互，用于设计 API/系统测试。
- `OBJ-*`：描述领域服务、实体和 Repository 协作，用于设计单元测试。
- `REQ01～REQ18`：细粒度功能及安全需求，通过《需求追溯矩阵》归入 `UC01～UC08`。

测试策略见[软件测试文档](./软件测试文档.md)，当前覆盖状态见[测试清单](./测试清单.md)，运行结果见[校园二手交易平台测试文档](./校园二手交易平台测试文档.md)。

## 2. 转换规则

| 模型元素 | 测试中的对应物 | 必须验证的内容 |
| --- | --- | --- |
| 参与者 | 测试用户和 Session Cookie | 身份来自服务端 Session，不相信请求体身份字段 |
| 系统事件 | MockMvc 或真实 HTTP 请求 | 路径、方法、参数、认证和 CSRF 正确 |
| 系统返回 | HTTP 状态和 JSON 投影 | 稳定结果、安全字段及错误语义正确 |
| 对象消息 | Service/Entity/Repository 调用 | 方法输入输出、异常和状态变化正确 |
| 状态转换 | 数据库最终状态 | 目标对象正确变化，无关对象保持不变 |
| 异常分支 | 反向或并发测试 | 未登录、无 CSRF、越权、重复、过期和竞争被正确处理 |
| 外部适配器 | Mock、Testcontainers 或 Mailpit | 邮件、MySQL 和图片存储边界可观察、可复现 |

每个场景至少包含主成功流程、一个业务异常分支、一个权限反向用例，以及关键持久化不变量。只断言 HTTP 2xx 或程序未抛错不算有效测试。

## 4. 示例：交易场景

根据 `SYS-SEQ05`，买家提交购买意向时测试应：

1. 创建卖家、买家和 `ON_SALE + VISIBLE` 商品。
2. 使用买家 Session 与 CSRF 调用购买意向接口。
3. 断言买家由 Session 推导，订单为 `PURCHASE_REQUESTED`，商品仍为 `ON_SALE`。
4. 使用卖家本人、重复请求、伪造 `buyerId` 和缺少 CSRF 的请求验证反向分支。
5. 创建第二位买家的意向，并发执行卖家接受操作。
6. 断言最多一条订单进入 `WAITING_HANDOVER`，商品最多形成一个 `RESERVED`。
7. 完成交接后断言订单为 `COMPLETED`、商品为 `SOLD`；取消或超时则释放预留。

这些断言分别落在 `TradingServiceTest`、`TradingApiIT` 和 `MySqlConcurrencyIT`，不在本文复制完整测试代码。

## 5. 共同安全约束

REQ18 不是独立业务场景，而是 UC01～UC08 的共同约束。每类受保护写操作至少验证：

1. 无 Session 请求被拒绝。
2. 有 Session 但无 CSRF 请求被拒绝。
3. 合法 actor 与 CSRF 请求成功。
4. 非 owner、非参与者或错误角色请求被拒绝。
5. 请求体伪造身份字段不能改变真实操作者。
6. 账号禁用或认证版本变化后，旧 Session 不能继续写入。

## 6. 维护规则

业务场景变化时先更新《业务场景（用例）清单》和顺序图，再同步《需求追溯矩阵》、测试代码与《测试清单》。运行数量、日期和通过结论只写入正式测试报告及 `docs/ai/WORKLOG.md`。
